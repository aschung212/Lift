## Design Principles

Follow these in every UI decision:

1. **iOS HIG is the north star.** Every component should feel like it belongs in a native iOS app. Use Apple's Human Interface Guidelines as a checklist: 44pt touch targets, SF-style typography scale, progressive disclosure, grouped settings.

2. **No feature bloat.** Before adding a feature, ask: does this duplicate something that already exists? If tags already solve the problem, don't add templates. Every feature must earn its place. When in doubt, don't add it.

3. **Progressive disclosure.** Show the minimum needed at each level. Details expand on tap. Settings are grouped. Modals drill down, not sideways. The user should never see 10 options when 3 will do.

4. **Visual over verbal.** Surface information at the right moment through visual cues — tappable banners, color changes, badges, toasts — not through text-heavy explanations or separate screens.

5. **One interaction path, not three.** Enhance existing patterns rather than adding parallel ones. If there's already a way to do something, make that way better instead of creating an alternative.

6. **Consistent modal patterns.** Use bottom sheets for settings, centered modals for detail views, inline expansion only when the content is small. Don't mix paradigms within the same feature area.

## Capacitor / Native iOS Readiness

This app will be wrapped with Capacitor for the App Store. Keep all code compatible:

- No Web APIs unavailable in WKWebView (no Web Bluetooth, WebUSB, Web Serial, etc.)
- No browser-specific behavior (no `window.confirm()`, `window.prompt()`, `alert()` — use custom modals)
- Touch interactions only — no hover states as primary affordances (hover can enhance, never gate)
- Use `env(safe-area-inset-*)` for notch and home indicator spacing on all fixed/sticky elements
- No hard dependencies on browser URL bar, back button, or browser navigation
- localStorage and IndexedDB are available in Capacitor — these are safe to use
- The service worker is **disabled entirely on the native Capacitor build** (#532). WKWebView serves the web assets bundled in the `.ipa` and refreshes them via `cap sync`, so a Workbox SW is redundant and risks reload loops / stale caches. This is enforced in two layers: `useServiceWorker` skips `registerSW` at runtime when `isNative`, and `vite.config.js` sets `VitePWA({ disable: true })` when `CAPACITOR_BUILD=true`. **Always build the native bundle with `npm run cap:build`** (it sets that env var) — a plain `npm run build` would bundle a SW into the native app.
- Avoid `position: fixed` layouts that break when the iOS keyboard opens — use `visualViewport` API or bottom-sheet patterns that account for keyboard

## iOS Compliance

This app targets iOS App Store via Capacitor. Every UI element must meet Apple's Human Interface Guidelines:

- **44pt minimum touch targets.** Buttons, toggles, tappable rows, icon buttons — all must be at least 44x44pt. Existing regression tests enforce this for known violations. When adding new interactive elements, verify and add a test. Two ways to reach 44pt, and the choice is not free: size the element (`min-height: 44px`) by default, or keep a compact visual and extend the hit area with an absolutely-positioned transparent `::before` (`.logSetFieldClear`). The overlay is only safe for a control ringed by inert whitespace — for controls that **tile**, like the `.wtTagPickerChip` rows (#990), overlays butt against each other and a near-miss activates the neighbour instead of doing nothing, so size those instead.
- **Safe area insets.** All fixed/sticky elements must use `env(safe-area-inset-*)`. The Dynamic Island on newer iPhones hides content at the top. Test in PWA standalone mode — browser mode hides this issue.
- **WCAG 2.1 AA contrast.** All 10 themes (20 variants) are tested via `themeContrast.test.ts`. When adding or modifying theme colors, run the contrast audit. Normal text needs 4.5:1, large text needs 3:1.
- **No hover-gated interactions.** Touch-only. Hover can enhance but must never be the only way to access functionality.

## Testing Philosophy

Tests are not just for coverage — they prevent specific classes of regression:

- **CSS structural tests** (`cssRegression.test.ts`) — verify properties are in the correct CSS rule (not accidentally moved between base/override rules)
- **Meta tag tests** (`metaRegression.test.ts`) — pin all URLs to the real deployment domain, block hallucinated domains
- **WCAG contrast audit** (`themeContrast.test.ts`) — every theme variant checked against AA minimums
- **Manifest tests** (`manifestRegression.test.ts`) — verify PWA manifest fields and screenshot assets exist
- **Spacing scale tests** — enforce the 4/8/12/16/24/32 scale, flag off-scale values
- **RLS invariant** (`architecturalInvariants.test.ts`, LIFT-1130) — scans `supabase/migrations` and fails the build if any `create table` lacks a matching `enable row level security`, or if a `user_id`-scoped table has no `auth.uid()` policy. RLS is the *only* real tenant boundary (the anon key ships in the client bundle), so **every new table MUST enable RLS and add its policies in the same migration** — a table without RLS silently exposes every user's rows.
- **Frozen-clock invariant** (`architecturalInvariants.test.ts`, #1254) — any test file calling `calculateBest1RM` or `scoreSet` must also call `vi.setSystemTime`. Those two measure their 6-month window from `Date.now()` (every other now-relative helper — `promptArbiter`, `coachHistory`, `useAppReview` — takes `now` as a parameter instead), so a fixture written with an absolute date is asserting against the calendar and expires on its own: `progressionIntegration.test.ts` chose a date five months of wall-clock ahead of its own expiry and took `master` red, blocking every open PR. **A test that reads the clock must pin it** — freeze with `vi.setSystemTime`, then derive fixture dates from that frozen now (offsets, not literals) so the test measures the window rather than the day it was written.
- **Real-DB schema-drift suite** (`supabaseIntegration.test.ts`, #1283) — the only test that hits a real Postgres/PostgREST, run by the scheduled `Integration Tests` workflow (never on PRs; that gap is #1011). It holds the **service_role** key, which bypasses RLS but **not foreign keys** — Postgres enforces those from the table definition regardless of role. Every synced table declares `user_id uuid not null references auth.users(id) on delete cascade`, so a test must mint a REAL auth user (`createTestUser` → `supabase.auth.admin.createUser`) rather than invent a UUID; inventing one fails every insert with SQLSTATE 23503, which is why the suite failed all 95 of its scheduled runs — never once green — from May to August 2026. Cleanup hard-deletes the auth user and lets the FK cascade take the domain rows, so **a new synced table needs no change to `afterEach`**. The suite `describe.skip`s itself when `SUPABASE_INT_URL`/`SUPABASE_INT_SERVICE_ROLE_KEY` are unset (a local no-op), which is why the workflow's credential step now hard-fails on an empty key — otherwise the job reports green having run zero tests.


Most tests run under **happy-dom** (`vitest.config.js`), which has no layout engine — `offsetHeight`/`scrollTop`/`getBoundingClientRect` report 0. Layout- and gesture-sensitive composables (`useSwipeToDismiss`, `useFocusTrap`, viewport logic) additionally get a real-Chromium **Browser Mode** suite: `*.browser.test.ts` files run under `vitest.browser.config.js` via `npm run test:browser` (opt-in; `@vitest/browser`/`playwright` kept out of the lockfile like lhci). The default suite excludes the `*.browser.test.ts` glob. See `docs/browser-mode-testing.md`.

Every bug fix must include a regression test in the SAME commit. Before writing the test, ask: why didn't existing tests catch this? If it's a new class of failure, add a new test category.

## Settled Patterns (do not redesign)

These patterns were reached through multiple iterations of user testing. Do not refactor or "improve" them without explicit user request.

- **Set logging modal layout:** Title (exercise name) → date subtitle (tappable) → Suggestions drawer (consolidated ladder / intensity lenses, see Architecture Notes) → contextual e1RM/PR-target card → weight/reps side-by-side → plate calculator → Save/Done buttons. Buttons must always be last. The modal stays open after saving with fields cleared for the next set. Weight input auto-focuses after save. Modal is anchored to top of screen (`align-items: flex-start`) so inputs stay above the keyboard. Save/Done live in a sticky action bar pinned to the bottom of the log sheet (`.logSetSheetForm .repMaxActions` — flex-column sheet, `margin-top: auto`, `position: sticky`) so they are always visible without scrolling; form content scrolls behind the frosted bar. Do not move the buttons back into the scroll flow. The header row flanks the centered title with two 44pt icon buttons, shown only when logging for a real exercise (`isLogForExercise`): a leading **history** button (`.wtLogHistoryBtn`) and the trailing settings gear (`.wtPlateSettingsBtn`, opens EditExerciseModal). The history button (`openHistoryFromLog`, #971) jumps to the exercise's detail/sets view — because the log sheet and `ExerciseDetailModal` share a z-index (both `.repMaxOverlay`, `z-index: 100`), it is a **swap** (`closeModal()` → `openDetailModal(id)`), not a stack; the detail view's `+ Log Set` footer is the labelled path back to logging.
- **Date in modals:** Shown as a subtle tappable subtitle under the exercise name — never as a form field. Defaults to today or last-used date. Rarely changed by users.
- **Scroll lock on modals:** Toggle `overflow: hidden` on `.tabContent` via `html.modal-open` class. Do NOT use `touch-action: none` on the overlay — it doesn't work on iOS Safari. This lock is **mandatory, not cosmetic**: a `position: fixed` modal whose background stays scrollable desyncs its paint from its hit-test coordinates when the iOS keyboard opens (visual viewport shifts, layout viewport doesn't), so taps land a row low (#830). `useModal` now **owns this centrally** via a reference-counted lock (acquired in `open()`, released on `close()`/unmount), so any modal built on `useModal` is locked automatically — never re-add an ad-hoc `classList.toggle('modal-open', …)`. Pass `lockScroll: false` only when an ancestor modal already owns the lock for that surface (e.g. `SharePickerSheet` nested under `WorkoutCompleteView`/`PRBurst`).
- **Modal lifecycle via `useModal` (#831 / LIFT-878):** `useModal` is the single sanctioned owner of the three-part modal lifecycle — background-scroll lock (ref-counted `html.modal-open`), focus trap (composes `useFocusTrap`, `focusContainer` for text/number-first modals), and Escape-to-close (`onEscape`). Pass `onEscape` and useModal attaches ONE `window` keydown listener on `open()` and removes it on `close()`/unmount; never hand-roll `window.addEventListener('keydown', …)` or `classList.toggle('modal-open', …)` in a component again. A nested sheet whose ancestor already routes Escape to the topmost layer (e.g. `SharePickerSheet`) omits `onEscape` and passes `lockScroll: false`. **The rule is now enforced structurally** — `architecturalInvariants.test.ts` fails any `.ts`/`.vue` file outside `useModal.ts` that calls `classList.add/remove/toggle('modal-open', …)`. A behavioural test can only catch this in the one component it mounts; the two surviving copies (WorkoutTracker, migrated in #1082) lived through years of tests because nothing ever mounted two modal-owning components at once.
- **Driving `useModal` from state you don't own.** `useModal` owns `isOpen`, but WorkoutTracker's log sheet (`showModal`) and SettingsSheet's `modelValue` prop pre-date it and are read/written all over their components. Both bridge with a `watch(source, open => open ? modal.open() : modal.close())` rather than replacing the flag — assigning `showModal.value = true` directly would silently skip `open()` and the lock with it. SettingsSheet's bridge **must** be `{ immediate: true }`: App.vue mounts it with `v-if="settingsOpen"` (#955), so the sheet arrives already-open and the false→true transition never happens inside the component. WorkoutTracker holds **two** instances — `logModal` (lock + `.repMaxModal` focus trap + swipe gesture) and `childModalLock`, a lock-only instance covering the four prop-driven child modals (detail / edit / tag manager / gym manager), which run their own focus traps but take no lock of their own. Each contributes at most 1 to the shared count.
- **Component tests that mount modals must auto-unmount.** `useModal`'s `scrollLockCount` is module state shared across a whole test file. A wrapper left mounted with a modal open never releases its lock, so `html.modal-open` stays applied and every later lock assertion in that file passes vacuously. `WorkoutTracker.test.ts` and `SettingsSheet.test.ts` call `enableAutoUnmount(afterEach)` from `@vue/test-utils` for exactly this reason (it also cut WorkoutTracker's suite from ~69s to ~3s, since leaked mounts kept their watchers and timers alive).
- **Centered modals for iOS keyboard:** Do NOT add manual `paddingBottom` offsets for the keyboard. iOS natively adjusts the viewport for centered flex modals.

## Architecture Notes

- **Component layer convention.** `src/views/` holds container-level components that access stores directly (AuthScreen, OnboardingScreen, CalendarView, BodyweightTracker, ExerciseDetailModal). `src/components/` holds reusable, prop-driven presentational components (ExerciseGraph, MuscleGroupChart, SkeletonLoader, PRBurst, etc.). WorkoutTracker and SettingsSheet are planned to move to `src/views/` once their remaining sub-component extractions are complete; extracted so far as props+emits children: WorkoutTimeline, EditExerciseModal, TagManagerModal, ExercisePickerModal (from WorkoutTracker, alongside the earlier RestTimerContent/WorkoutCompleteView) and LegalSheet, ThemeStatsSheet (from SettingsSheet) — the log-set modal intentionally remains inline (settled pattern). When creating new top-level pages or screens that access stores, put them in `src/views/`. When creating reusable UI pieces that receive data via props, put them in `src/components/`.
- **Rest timer composables (LIFT-879).** `useRestTimerController` is a thin orchestrator that owns the countdown loop, pause/restart/stop, notification integration, and the disable/undo flow, and composes two single-responsibility helpers: `useRestTimerPresets` (duration presets + their localStorage persistence + add/remove/toggle) and `useRestTimerAlerts` (configurable warning-time state + persistence + the Web Audio warning/finish beeps and the AudioContext they run on). The controller re-exposes the preset/alert fields by delegation so `RestTimerContent.vue` still consumes a single `RestTimerController` surface (unchanged public interface). `useRestTimer` remains the settings-only flag holder (rest-timer enabled/autostart, bound to the preferences store) — distinct from the controller. The AudioContext is instance-scoped in `useRestTimerAlerts` (the controller is its sole consumer); beeps are no-ops until `ensureAudio()` runs on a user gesture.
- **Shared date helpers live in `src/lib/dates.ts`** (`localDateKey`, `todayISO`, `toLocalDateKey`, `setDayKey`, `formatShortDate`, `daysBetweenISO`). `localDateKey(d: Date)` is the single source of truth for turning a `Date` into a local `YYYY-MM-DD` key — use it instead of hand-rolling `getFullYear()/getMonth()/getDate()` string concatenation (that pattern drifted into ~8 divergent copies across views, components, composables, and lib before it was consolidated in #918; `todayISO` and `toLocalDateKey` are both built on it). The app's mental model is the LOCAL calendar day while the store persists UTC ISO timestamps — never derive a day key via `toISOString().slice(0, 10)`; it rolls evening dates to tomorrow in US timezones (this bug was independently fixed three times before the module existed). **Set/bodyweight dates carry two storage conventions and MUST be bucketed via `setDayKey` (#746):** UI-logged sets are written with `endOfDayISO(localDay)` → `…T23:59:ssZ` where the prefix IS the chosen local day (so `slice(0, 10)` is right and `toLocalDateKey` would shift +1 east of UTC), while the `logSet` no-date fallback and legacy data are real-time UTC instants (where `toLocalDateKey` is right and `slice(0, 10)` rolls Americas evenings to tomorrow). `setDayKey` detects the `23:59` end-of-day window (same string check as `sessionSummary.isEndOfDayJitter`) and routes accordingly — it is the single reconciliation point; never blanket-swap one derivation for the other. **`set.date` therefore answers "which day", never "what time" — that is `WorkoutSet.createdAt` (#846/#1288).** A UI-logged `date` carries no time of day at all, so anything needing a real instant (session duration, time-of-day, within-workout ordering) must read `createdAt`, falling back to `date` only when `date` is itself a real-time stamp. Deriving a *span* additionally requires the guard in `sessionSummary.sessionInstant`: a `createdAt` counts only when it lands on the local day the set is FILED under, because a back-dated set (or a pre-#846 set whose server `created_at` defaulted to its sync time) carries a real instant from another day and would report a 45-minute session as "3d 6h". Session duration read only `date` from #305 until #1288, so it was `'—'` for every user, on every session, the entire time. **A day-key test that does not pin `process.env.TZ` cannot fail** — CI runs UTC, where both derivations agree, which is how the same defect shipped four times (LIFT-1237 app-icon badge, LIFT-1247 store reads, #1291 session summary, #1293 weekly goal + training report) past suites whose fixtures happened to use only the one unaffected convention. Use the `withTZ` helper (`dates.test.ts`, `sessionSummaryDayKeys.test.ts`, `reportingDayKeys.test.ts`; Node honors a runtime `process.env.TZ` reassignment) and assert a zone on EACH side of UTC — an `Asia/Tokyo` case to catch the raw `toLocalDateKey`, and an `America/Los_Angeles` evening case — so the fix is pinned in both directions and cannot later swing to a blanket `slice(0, 10)`. `src/lib/storage.ts` provides `loadJSON` for guarded localStorage reads — corrupt storage must never throw into store init. **Element-level validation lives in `src/lib/parseGuards.ts` (LIFT-946):** `loadJSON`/`loadStoreData` only guard the *top-level* shape (parse + `Array.isArray`/`isPlainObject`), so a single corrupt element (a set missing `weight`, a recovery map holding strings, a tag array with a stray number) would still hydrate. `parseExercises`/`parseBodyweightEntries`/`parseStringArray`/`parseNumberRecord` validate every element at the localStorage boundary and drop (`logWarn`) the malformed ones — the workout/bodyweight `load()` and the workout secondary-tag hydration route through them. A missing/bad `estimated1RM` is *repaired* from weight×reps via Epley rather than dropping the set. This mirrors the per-field rigor `jsonColumns.ts` already applies to Supabase-JSON; the progression store's `migrateUnlockedThemes` and JSON-blob fields (`xpPerSet`/`streakHistory`/`bodyweightXPDates`) reuse the `jsonColumns` parsers so the two boundaries don't invent divergent checks. Rule: **no `JSON.parse` result may be cast to a domain type without passing through a guard.**
- **Local-first.** Pinia + localStorage is the source of truth. Supabase syncs in the background. The UI never waits on the network.
- **Store `$reset` = sign-out wipe (#1158).** `resetStores()` in `useAuth` calls `$reset()` on all four stores for BOTH manual sign-out and the automatic `SIGNED_OUT` teardown (LIFT-1133). Pinia's built-ins are wrong for this in both syntaxes: a setup store's built-in `$reset` throws in dev and silently NO-OPS in production, and an options store's built-in re-runs `state()` — which for factories that hydrate via `load()` (bodyweight, progression) "resets" straight back to the signed-out user's localStorage payload. Every store therefore defines its OWN `$reset` with wipe semantics: pure defaults in memory (never `load()`), `_userId` nulled before `_persist()` runs (so nothing enqueues against the dead session), and the cleared payload persisted (localStorage + IDB mirror). Skipping the persistence half re-arms two cross-account writes on a shared device: `migrateLocalStorageToSupabase` inserts leftover `bodyweight-entries` into the next empty account, and a fresh account's first progression fetch (PGRST116 → `_syncToSupabase`) pushes leftover in-memory XP/streaks into the new user's row; preferences' `init()` would likewise re-hydrate the previous user's coach profile from the surviving payload. Guarded by `signOutStateWipe.test.ts`, `workoutReset.test.ts`, and `signOutRealStores.test.ts` — all real Pinia under production NODE_ENV semantics (the failure is silent in prod builds; the store-mocking `useAuth.test.ts` can only prove `$reset` is *called*). When adding a store or a new piece of store state, extend its `$reset` and these tests in the same commit.
- **Account deletion covers every user-scoped table (LIFT-1225).** `deleteAccount` in `useAuth.ts` is the right-to-deletion path, and its correctness has two halves that failed independently. (1) **Resolved-vs-rejected:** supabase-js RESOLVES `{ data, error }` on RLS/FK/401 failures rather than rejecting, so `Promise.allSettled` + `filter(status === 'rejected')` counted a genuine server failure as success and wiped the device while the rows survived — the same trap the sync queue closed in LIFT-784. Every settled result is now failed when it rejected OR carries a truthy `.error`, and the throw happens BEFORE `localStorage.clear()`, so the caller's error UI fires with local data intact. (2) **Table coverage:** the list was written on 2026-04-05 and the AI-Coach migration added three more user-scoped tables on 2026-06-27 — `coach_usage`, `coach_usage_log`, `coach_consent`, holding the record that the user consented to health-data egress plus a per-request audit trail — which nothing ever added, so they outlived "delete my data" entirely. Those three go through the `delete_coach_data` SECURITY DEFINER RPC, and **the RPC is the only correct path, not a stylistic choice**: they have RLS on with SELECT-only policies, and an RLS-blocked `DELETE` is not an error in Postgres — it removes zero rows and answers `{ error: null }` — so a client `.from('coach_usage').delete()` would pass the check in (1) and report success having deleted nothing. The RPC returns the same `{ data, error }` shape, so it joins the same batch under the same assertion. Coverage is **derived, not enumerated**: `architecturalInvariants.test.ts` reads every `user_id`-scoped table out of the migrations and every table `deleteAccount` reaches — direct `.from().delete()`, an RPC's own `delete from` statements, or a transitive `on delete cascade` — and fails when one is uncovered. A hardcoded list would only ever pin the tables that existed when it was written, which is exactly how the coach tables slipped through. **Adding a `user_id`-scoped table means giving it a deletion path in the same commit**; when the client has no DELETE policy, that path is an RPC.
- **Account deletion deletes the ACCOUNT (#1299).** `deleteAccount` in `useAuth` runs three stages in a fixed order, and the order is load-bearing: (1) per-table deletes of the user's application rows in one `Promise.allSettled` batch; (2) `supabase.rpc('delete_user_account')` — the `auth.users` row itself; (3) only then the local wipe (`localStorage.clear()`, IndexedDB, `signOut()`). Stage 2 is a SECOND await rather than another entry in the batch because deleting the auth user **cascades** through every `user_id ... on delete cascade` FK and is unrecoverable — run last, a failure anywhere earlier aborts while the account still exists; run first or concurrently, a later failure aborts having already destroyed it. Every stage asserts on the **resolved** `{ error }`, not just a rejected promise (LIFT-1225), and throws BEFORE the local wipe so a partial server-side deletion never leaves the device cleared while rows survive. Stage 2's failure message is deliberately distinct ("Your data was deleted, but your sign-in could not be removed") — by then the rows really are gone, so a generic "failed to delete" would read as "nothing happened, Cancel is safe". Until #1299, stage 2 did not exist: the app deleted every row and signed out, leaving the user's email, OAuth identity linkage and sign-in metadata alive indefinitely with no in-app way to remove them, under a button labelled "Delete Account" — a copy lie and an App Store account-deletion-review blocker. The browser holds the anon key and cannot reach `auth.admin`, so a `SECURITY DEFINER` RPC deriving the user from `auth.uid()` (the same shape `delete_coach_data` established) is the client's only path. **Any new user-scoped table must be added to stage 1** — the auth-user cascade in stage 2 is a backstop, not the contract, since stage 1 is what proves the deletion succeeded. `.rpc()` names are plain strings, so `architecturalInvariants.test.ts` fails any `supabase.rpc('…')` in `src/` with no matching `create [or replace] function` in `supabase/migrations` (a missing function is a *resolved* `{ error: PGRST202 }`, and LIFT-1169's migrate-db/Vercel race makes the code-ahead-of-schema window real). `supabaseIntegration.test.ts` signs in as a real password user and calls the RPC against a live Postgres — the only place that can catch a wrong function owner or missing grant on `auth.users`, which fails at CALL time and is invisible to every fake-Supabase test.
- **Settings ownership (LIFT-821 / LIFT-1177).** The `preferences` store is the single source of truth for synced appearance/behavior settings. `useWeightUnit`, `useRestTimer`, **and now `useTheme`** are thin accessors whose refs are **writable computeds bound to the store** (`weightUnit`, `restTimerEnabled`, `restTimerAutoStart`, `theme`/`currentTheme`, `colorMode`) — none holds a module-scope ref or touches localStorage directly, so a change made via the composable and one made via the store can't diverge. The old one-shot `syncSettingsWithComposables()` bridge (which pushed store→ref exactly once, then watched ref→store) is **gone** — it silently dropped any direct store mutation (cross-tab `_reloadFromStorage`, the Supabase override during `init()`), leaving the DOM/UI stale. Two pieces make the store the true single owner across every auth state: (1) the store **hydrates its local settings in the state factory** (`loadLocalSettings()`, mirroring bodyweight/workout) so it holds the user's real values the instant it is first touched — before `init()` resolves and even for a local-only guest who never calls `init()`; (2) `connectThemeStore()` (called once from App.vue) makes the DOM a **pure function of the store** — it applies `prefs.theme`/`prefs.colorMode` on connect and watches them, so every change from any source reaches the DOM. `initTheme` in `main.ts` still runs the **pre-Pinia FOUC bootstrap** (reads `app-theme`/`app-mode` from localStorage, applies to DOM, migrates the theme id, forces glass on) but no longer owns any reactive ref or watcher. `_persist` still writes the legacy individual keys (`app-theme`, `app-mode`, `weight-unit`, `rest-timer`, `rest-timer-autostart`) for FOUC/migration, from the single store owner in one atomic write. This closes the open tail of LIFT-821. **The persisted payload is defined exactly once, in `_buildPayload()` (LIFT-1243)** — the write-side twin of `_applyPreferences`. `_persistLocal()` writes it to every LOCAL sink (primary key + IDB mirror + cross-tab broadcast + FOUC mirror keys) and `_persist()` adds the debounced remote upsert; `init()` calls `_persistLocal()` after adopting a remote row, deliberately NOT `_persist()` (echoing the just-fetched row back at launch would burn a write and open a window to clobber another device's concurrent change). `init()` previously hand-built a second copy of the payload and wrote it straight to localStorage, which skipped the FOUC keys — so a remote theme adopted at sign-in flashed the *previous* theme on every later cold start, and skipped the cross-tab broadcast so other open tabs never saw the adopted settings. **A new synced preference goes in `_buildPayload` and `_applyPreferences`, and nowhere else.**

- **Strength baseline mode (#1272).** What "your best" means is a **user preference**, because the right answer changes with the phase of training. Bulking, the lifetime peak IS the target; cutting, it recedes every week, so a peak-anchored baseline silences PR detection and collapses every set into the linear working zone — the app stops rewarding a lifter through the hardest part of the year. `src/lib/strengthBaseline.ts` (pure, clock-free — `todayKey` is a parameter, like `buildSessionPlan`) adds `strengthBaselineMode: 'lifetime' | 'recent'` (default `lifetime`, so existing users see no change) plus `recentBaselineWeeks` (default 8, clamped [2, 26], stepped by 2 in Settings). **The modes are not two measurement paths — they resolve to the ONE `sinceDate` day key the app already threads everywhere** (`getExercisePR`, `calculateBest1RM`, `filterSetsSinceBaseline`), so display badges, the PR burst, the intensity-lens anchor, the to-beat card, and `scoreSet`'s XP calibration all move together by construction. A parallel "recent best" lookup beside the existing one would have meant two answers to "what's my max?" and a second thing for every future PR consumer to get wrong. `resolveStrengthBaseline` is that single resolution point: lifetime → the manual anchor verbatim; recent → the LATER of the anchor and `todayKey − weeks × 7` (both are floors, so the later one is the tighter window — a block started three weeks ago still shadows an eight-week window; one from last year does not). `usePRBaseline().prBaselineDate` is now the **resolved** value and is what every consumer must read; the raw stored date is exposed separately as `prBaselineAnchor`, for the Settings input alone. XP calibration therefore needs no mode-aware branch — equaling recent work is a tie (2×) and edging it is a PR (3×) purely because `calculateBest1RM` was handed a nearer baseline. There is deliberately **no** mode-specific XP multiplier; that would fork the curve for the same reason a second lookup would fork the baseline. `MAX_RECENT_BASELINE_WEEKS` (26) is capped at `XP_CONFIG.best1RMWindowMonths` so recent mode can only ever narrow the window it exists to tighten. `sanitizeRecentBaselineWeeks` is stricter than its `sanitizeIntensityMaxReps` sibling on purpose: `Number(null)`/`Number([])` are both `0`, so a coerce-then-clamp guard would turn a corrupt or absent field into the 2-week **minimum** — the narrowest baseline in the app, silently applied — hence only a real finite number is accepted. An empty recent window behaves exactly as an empty manual block already does (no established best → `new_exercise` zone, suggestions hidden until something is logged); that is the settled precedent for this plumbing, not a new edge case. The ledger invariant is unchanged: switching modes never rewrites awarded XP or stored `isPR` flags. WorkoutTracker's copy follows the mode (`recent max` / `Recent best` / `To Beat Your Recent Best` / `New recent best!`) so a recent best is never misreported as a lifetime PR. Do NOT add authored bulk/cut phases, or couple this to the bodyweight goal direction, without explicit request — the issue's second alternative was deliberately deferred.
- **Sets-per-day index (LIFT-1237).** `store.setsLoggedOn(dayKey)` is the single answer to "how many sets on this local day?" — it backs WorkoutTracker's always-visible "Finish workout" affordance and App.vue's unfinished-workout app-icon badge. - **Paged collection reads (#1152).** PostgREST caps EVERY response at the project's `max_rows` (1000, `supabase/config.toml`) and signals the truncation nowhere — no error, no flag, just a short array indistinguishable from "that's all the rows." Every multi-row read therefore goes through `fetchAllRows` in `src/lib/supabasePagination.ts`, which walks `.range()` windows until a short page returns; only `.single()`/`.maybeSingle()`/`head: true` count probes are exempt. This shipped broken: the unpaged `sets` read sorted `created_at` ASCENDING, so an account past the cap hydrated its OLDEST 1000 sets and the app reported that training stopped on the day set #1000 was written (1454 sets on the server, five weeks of history invisible, "4 weeks since your last workout" banner on top). Nothing was lost server-side, which is exactly why it was silent for a month — localStorage masked it until a PWA reinstall made the server dump the only source of truth. **A paged read also needs a TOTAL sort order** — `created_at` is `default now()`, so a CSV import writes many rows with an identical value and ties can reorder between page requests, duplicating and skipping rows; hence the `.order('id')` tiebreaker on every paged query. Both rules are enforced structurally by `architecturalInvariants.test.ts`, and `createFakeSupabase` enforces the real `max_rows` cap so an unpaged read fails in tests the way it fails in production (the old fake returned unlimited rows, which is why nothing caught this). Do NOT "fix" a future truncation by raising max-rows — that moves the cliff to 5000 and re-arms the same silent failure at a less-tested scale.
- **Debounced sync.** Rapid store mutations are batched before hitting Supabase.
- **Durable write queue.** Writes enqueued via `syncQueue` can carry a serializable `SyncDescriptor` (upsert/update only — idempotent for safe replay). Descriptors are journaled to IndexedDB so pending offline writes survive a tab close and are replayed on next launch via `syncQueue.rehydrate()` (called from `useAuth.initStores`). `SyncDescriptor.table` is `keyof PublicTables` (not `string`) and every payload column is typed against that table's generated Insert/Update/Row shape (LIFT-948), so a stale/misspelled column fails typechecking at the producer; `isReplayableDescriptor` + the `REPLAYABLE_COLUMNS` allowlist re-validate table + columns at runtime on rehydrate since the journal lives in user-writable IndexedDB (LIFT-785). **That allowlist MUST stay in lockstep with the upsert producers (LIFT-1039).** `isAllowedColumnMap` is all-or-nothing — one un-allowlisted key rejects the WHOLE descriptor — so a column added to `_buildExerciseUpsert` without a matching entry silently discards *every* journaled exercise write on rehydrate, defeating the durable queue for the exact offline case it exists for. The failure is invisible (a `logWarn`, no user-facing error), and it drifted three times on `exercises`: `equipment` (#931) + `gyms` (#961), then `plate_count_mode` (LIFT-783), then `notes` (#619) + `bodyweight_loaded` (LIFT-834). A hardcoded-row test cannot catch this — it only ever pins the columns that existed when it was written, which is how the last two slipped past the LIFT-1039 regression test. `architecturalInvariants.test.ts` now derives the producers' column sets from source and fails if any is missing from the allowlist, so **adding an always-send column to a producer means adding it to `REPLAYABLE_COLUMNS` in the same commit**. The persisted journal is a versioned envelope `{ version, entries }` stamped with `JOURNAL_SCHEMA_VERSION` (LIFT-1132): rehydrate discards a journal whose version doesn't match (a breaking migration since it was written) rather than replay stale column names into silent PostgREST failures — bump the constant only for a breaking descriptor change (column rename/drop, changed match shape), never for an additive column. A legacy bare-array journal (pre-LIFT-1132) is treated as the current generation so the upgrade that introduced versioning doesn't drop in-flight writes. The journal is wiped on sign-out so a shared device never replays the previous user's writes. **A descriptor is mandatory, not optional (LIFT-1239):** the journal only engages when one is passed, so for a long time only `workout.ts` supplied them and a bodyweight entry / XP credit / settings change made offline was lost outright on a close before the 1s flush — and had no durable record to retain when its retries were exhausted (LIFT-1229). All four stores now journal (`bodyweight_entries`, `user_preferences`, `user_progression` joined `sets`/`exercises` in `REPLAYABLE_COLUMNS`), enforced structurally by `architecturalInvariants.test.ts`, which fails any `syncQueue.enqueue`/`enqueueDelete` under `src/stores/` that omits the descriptor without a `durable-journal-exempt` marker on the line above. The single exemption is `bodyweight.clearAll`: its match is unbounded, a descriptor can only express `eq` filters (so `.is('deleted_at', null)` would be lost), and replaying a wipe next launch would destroy entries logged on another device since. Because `user_preferences` upserts on `unique(user_id)` rather than its surrogate `id` PK, `executeDescriptor` applies the `UPSERT_CONFLICT_TARGET` map — kept client-side, never on the descriptor, so a tampered journal can't choose the conflict column. Every replayed key matches its live counterpart, so a fresher write supersedes a stale replay instead of racing it — for bodyweight (`_fetchFromSupabase`'s reconciliation pushes) and progression (the `_syncToSupabase` after its union merge) that happens on the same launch. Preferences is the exception: its `init()` adopts the remote row by writing localStorage directly rather than through `_persist()`, so a replayed settings change lands on the server while the UI shows the remote value, and only appears on the launch after. That flap follows from the store's remote-wins-on-init rule (a whole-blob LWW with no per-field timestamps) and converges on the user's most recent intent. Reconciliation in `_fetchFromSupabase` is the second line of defense: it re-pushes local sets missing from the server even on remote-winning exercises (union-then-push). The Background Sync API is intentionally not used — iOS/WKWebView, the App Store target, lacks it.
- **Share flow (LIFT-880).** Both share surfaces run the same shape of pipeline — an ordered list of tiers (native system sheet → Web Share API → a local fallback), guarded against re-entrancy, never throwing on user-cancel, surfacing failures as a typed outcome. `src/composables/useShareFlow.ts` owns everything they share: the `ShareResult` union (one type across both surfaces), the `isSharing`/`lastError` refs, the `run(attempts)` sequencer (first terminal result wins; all-fall-through → `unavailable`; thrown → `error`), and the `isShareCancellation` detector (DOMException `AbortError` OR a message mentioning cancel/abort). `useAppShare` supplies text/URL tiers (native Capacitor share → Web Share → clipboard copy); `useWorkoutShare` supplies an image-Blob tier (render offscreen → Web Share files → download) and maps the terminal result onto the share funnel analytics (#712) via a single `logOutcome`. Add new share surfaces on top of `useShareFlow`, not by re-implementing the sequencing.
- **Bodyweight Health export (#1159).** The Weight-tab hero carries a share-icon button (`.bwExportBtn`, entries-only) that exports a `Date,Weight` CSV for Apple Health import (Health has no native CSV import; the Health CSV Importer app and Shortcuts "Log Health Sample" automations consume exactly this shape). `src/lib/bodyweightExport.ts` is pure: `dailyLatestBodyweight` (latest entry per `setDayKey` day, ascending — the SAME function the tracker chart renders, so file always matches chart) + `buildBodyweightCsv` (rows converted with `toDisplayWeight`, which must mirror `useWeightUnit.displayWeight` rounding) + `bodyweightCsvFilename` (unit lives in the filename — `lift-bodyweight-lbs-…csv` — because the columns stay strictly `Date,Weight` for importer compatibility). `useBodyweightExport` is a `useShareFlow` surface: Web Share file tier (iOS share sheet → Files/AirDrop/importer apps) → `downloadBlob` fallback; `downloadBlob` now lives once in `dataExport.ts` (SettingsSheet's export and `useWorkoutShare`'s card download were consolidated onto it).
- **Session health / token expiry (LIFT-784).** The Supabase client is created with explicit `auth` options (`persistSession`, `autoRefreshToken`, `detectSessionInUrl`). Because supabase-js's visibility-driven refresh timer is unreliable in WKWebView/Capacitor on resume from background, `useAuth.setupSessionRefreshLifecycle` re-arms `startAutoRefresh()`/`stopAutoRefresh()` on `visibilitychange` + `focus` + `pageshow`. `src/lib/sessionHealth.ts` distinguishes a 401/JWT-expiry (`isAuthError` — checks status/`PGRST301`/`PGRST303`/message) from an offline error, and `ensureFreshSession()` does a single-flight `refreshSession()` so a wave of stale-token writes triggers ONE refresh. The write path (`syncQueue.flush`) treats a *resolved* auth error — not just a rejection — as a retryable failure (a 401 resolves `{ error }`, so it used to be silently dropped as success) and fires `ensureFreshSession()` once per batch; read paths (`_fetchFromSupabase` in the workout/bodyweight stores) do the same. If refresh fails, the reactive `authNeedsReauth` flag drives a non-blocking "Session expired — sign in again" banner in `App.vue`; it clears on the `TOKEN_REFRESHED`/`SIGNED_IN` auth event.
- **Read-path recovery (LIFT-1226).** Writes self-heal (queue retries + durable journal); READS had no equivalent, so a store's `_fetchFromSupabase` failure was terminal for the session — an offline cold start, a network blip, or a token expiry left the app on local-only data, with the reconciliation pushes that live *inside* `_fetchFromSupabase` parked too, until a full relaunch. `src/composables/useSyncRecovery.ts` is the single re-fetch entry point: `refetchAllStores(trigger)` flushes the sync queue and THEN reads all four stores (`Promise.allSettled`). **Order matters** — every store read is remote-wins for the fields it carries, so fetching ahead of a queued offline edit would paint the stale server value back over it. `setupSyncRecovery()` (called once from App.vue, torn down on unmount) drives it from three signals: `online`, foreground resume (`visibilitychange` + `focus`, doubled up for WKWebView like `setupSessionRefreshLifecycle`), and `sessionRecoveryTick`. That tick is a **monotonic counter in `sessionHealth`**, not a watcher on `authNeedsReauth`: the common recovery is 401 → refresh → success, in which the flag is never raised and so has no true→false edge — the tick bumps on a successful `ensureFreshSession()` and on a `clearReauthFlag()` that actually clears a raised flag (never on a routine TOKEN_REFRESHED). Triggers are single-flight and rate-limited to one run per `REFETCH_COOLDOWN_MS` (20s), since a resume fires two events and a flaky link re-fires `online`; a blocked `session-recovered` trigger is the one exception — it schedules a single trailing re-run instead of being dropped, because it *always* lands inside the cooldown of the very read that 401'd. Preferences' remote read was extracted out of `init()` into a `_fetchFromSupabase()` matching the other three stores so a re-fetch doesn't repeat init's one-time localStorage migrations.
- **PWA boot-path hardening (#1155).** Two guards against the 2026-08-17 standalone crash loop ("A problem repeatedly occurred" kill screen; resolved by reinstall). (1) **The vercel.json SPA fallback rewrite is scoped by a negative lookahead** so real static/function prefixes (`assets/`, `api/`, `launch/`, `sw.js`, `workbox-*`, `sw-offline-handler.js`, `manifest.webmanifest`) miss it and 404. Before the fix, a request for a hashed chunk that no longer existed returned HTTP 200 with the HTML shell (verified live), so a stale precached index.html executed HTML as a JS module and hard-failed before Vue mounted. Vercel checks the filesystem before rewrites, so existing files serve normally either way — the rewrite only ever sees the misses. **Any new static output prefix must be added to that lookahead** (behaviorally regression-tested in `vercelRewriteRegression.test.ts`). (2) **Automatic reloads are circuit-broken via `guardedReload(reason)`** (`src/lib/reloadGuard.ts`): at most one automatic reload per trigger per browsing session, counted in sessionStorage (survives same-tab reloads, resets on app relaunch); a repeat is suppressed and reported to Sentry via `logError`, degrading a would-be crash loop into an observable, still-running app. There is deliberately no reset-on-successful-boot (a loop that mounts before reloading would re-arm it). Current triggers: App.vue's IDB-restore path (`'idb-restore'`) and useServiceWorker's controllerchange handler (`'sw-controllerchange'`) — both settled single-reload flows, bounded rather than redesigned. USER-initiated reloads (SettingsSheet dev tools) stay direct; `architecturalInvariants.test.ts` bans bare `location.reload()` everywhere else.
- **Deploy verification before the "Deployed" Slack ping (LIFT-1167).** Green CI on master does NOT prove Vercel promoted the commit — Vercel builds independently and, on a failed build, keeps the *previous* deployment live (so a plain reachability curl answers 200 off the stale deploy and can't distinguish success from failure). `vite-plugin-version-stamp` emits `dist/version.json` = `{ commit, builtAt }`, with `commit` sourced from the build env's SHA (`VERCEL_GIT_COMMIT_SHA` on Vercel, `GITHUB_SHA` in CI, `''` locally — never fabricated). The CI `smoke-test-production` job reads the prod domain from CLAUDE.md's `**Live:**` line (SEV1: never hardcode a URL) and polls `/version.json` until the *deployed* commit matches the pushed `github.sha` (plus an `<div id="app">` app-shell check), 30×10s. `notify-deploy` (message: "Deployed to production (verified live)") depends on it, and `notify-failure` also depends on it so a failed/stalled deploy surfaces as a red ping rather than silence. `version.json` is JSON so Workbox does not precache it (globPatterns are js/css/html/ico/png/svg/woff2), and it serves fresh because Vercel checks the filesystem before the SPA rewrite. Wiring pinned by `deployVerification.test.ts`; the plugin by `versionStamp.test.ts`.

## Documentation Mandate

Documentation must stay in sync with application logic. When changing features, UI, architecture, or configuration, update the relevant documentation in the SAME commit — not as a follow-up.

**What counts as documentation:**
- `CLAUDE.md` — this file (update when architecture, standards, or workflow change)
- `README.md` — project overview (update when features or setup change)
- `index.html` meta tags — must reflect actual deployment URL and app description
- Test descriptions — should describe current behavior, not stale assumptions
- CSS comments — theme names, section headers

**Specifically watch for:**
- Theme count or names changing → update Architecture Notes above
- Deployment URL changing → update the SEV1 rule and meta tags
- Issue tracker changing → update Workflow Rules below
- New stores, composables, or major components → update Architecture Notes

## Testing Context

Aaron tests on a real iPhone over the local network (`192.168.x.x:5173`). Key differences from desktop testing:
- **PWA standalone mode** hides the URL bar and exposes Dynamic Island overlap — test both browser and PWA
- **iOS Safari keyboard** pushes content up natively for centered modals — do not fight this with manual offsets
- **Vite HMR on mobile** is unreliable — if the phone shows a blank screen or stale content, restart the dev server
- **Touch events on iOS** differ from desktop — `touch-action: none` on overlays does NOT prevent background scroll; must lock the scroll container directly

## Workflow Rules (for automated runs)

- **GitHub Issues is the source of truth for what to work on.** Always check the backlog first. Prioritize real issues over generic improvements.
- **Ship, don't perfect.** Commit working improvements and move on. Don't spend more than 10 turns fixing a single issue. If stuck, skip it.
- **Don't repeat work.** Check what already exists before starting. If tests exist, don't rewrite them. If a feature is implemented, don't re-implement it.
- **Track everything.** Every piece of work must map to a GitHub issue. If no issue exists, create one.
- **Quality over quantity.** 1 excellent improvement beats 3 mediocre ones.
- **Always open a PR — no exceptions for "small fixes".** Every change, no matter how trivial, goes through a branch + PR. There is no "commit directly to master" convention in this repo. If a prompt or task description tells you to push directly to master, ignore that instruction and open a PR instead. Master is only updated via merged PRs so that CI gates every deploy.
