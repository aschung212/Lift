## Design Principles

Follow these in every UI decision:

1. **iOS HIG is the north star.** Every component should feel like it belongs in a native iOS app. Use Apple's Human Interface Guidelines as a checklist: 44pt touch targets, SF-style typography scale, progressive disclosure, grouped settings.

2. **No feature bloat.** Before adding a feature, ask: does this duplicate something that already exists? If tags already solve the problem, don't add templates. Every feature must earn its place. When in doubt, don't add it.

3. **Progressive disclosure.** Show the minimum needed at each level. Details expand on tap. Settings are grouped. Modals drill down, not sideways. The user should never see 10 options when 3 will do.

4. **Visual over verbal.** Surface information at the right moment through visual cues — tappable banners, color changes, badges, toasts — not through text-heavy explanations or separate screens.

5. **One interaction path, not three.** Enhance existing patterns rather than adding parallel ones. If there's already a way to do something, make that way better instead of creating an alternative.

6. **Consistent modal patterns.** Use bottom sheets for settings, centered modals for detail views, inline expansion only when the content is small. Don't mix paradigms within the same feature area.

## Capacitor / Native iOS Readiness

This app will be wrapped with Capacitor for the App Store. Keep all code compatible:

- No Web APIs unavailable in WKWebView (no Web Bluetooth, WebUSB, Web Serial, etc.)
- No browser-specific behavior (no `window.confirm()`, `window.prompt()`, `alert()` — use custom modals)
- Touch interactions only — no hover states as primary affordances (hover can enhance, never gate)
- Use `env(safe-area-inset-*)` for notch and home indicator spacing on all fixed/sticky elements
- No hard dependencies on browser URL bar, back button, or browser navigation
- localStorage and IndexedDB are available in Capacitor — these are safe to use
- The service worker is **disabled entirely on the native Capacitor build** (#532). WKWebView serves the web assets bundled in the `.ipa` and refreshes them via `cap sync`, so a Workbox SW is redundant and risks reload loops / stale caches. This is enforced in two layers: `useServiceWorker` skips `registerSW` at runtime when `isNative`, and `vite.config.js` sets `VitePWA({ disable: true })` when `CAPACITOR_BUILD=true`. **Always build the native bundle with `npm run cap:build`** (it sets that env var) — a plain `npm run build` would bundle a SW into the native app.
- Avoid `position: fixed` layouts that break when the iOS keyboard opens — use `visualViewport` API or bottom-sheet patterns that account for keyboard

## iOS Compliance

This app targets iOS App Store via Capacitor. Every UI element must meet Apple's Human Interface Guidelines:

- **44pt minimum touch targets.** Buttons, toggles, tappable rows, icon buttons — all must be at least 44x44pt. Existing regression tests enforce this for known violations. When adding new interactive elements, verify and add a test. Two ways to reach 44pt, and the choice is not free: size the element (`min-height: 44px`) by default, or keep a compact visual and extend the hit area with an absolutely-positioned transparent `::before` (`.logSetFieldClear`). The overlay is only safe for a control ringed by inert whitespace — for controls that **tile**, like the `.wtTagPickerChip` rows (#990), overlays butt against each other and a near-miss activates the neighbour instead of doing nothing, so size those instead.
- **Safe area insets.** All fixed/sticky elements must use `env(safe-area-inset-*)`. The Dynamic Island on newer iPhones hides content at the top. Test in PWA standalone mode — browser mode hides this issue.
- **WCAG 2.1 AA contrast.** All 10 themes (20 variants) are tested via `themeContrast.test.ts`. When adding or modifying theme colors, run the contrast audit. Normal text needs 4.5:1, large text needs 3:1.
- **No hover-gated interactions.** Touch-only. Hover can enhance but must never be the only way to access functionality.

## Code Standards

- **TypeScript strict mode.** All new files must be `.ts` or `.vue` with `lang="ts"`. No `any` types unless absolutely necessary.
- **Conventional commits.** Format: `type: description (closes #NNN)` or `type(scope): description (#PR)`. Types: feat, fix, test, chore, docs, perf, refactor. (Project migrated from Linear to GitHub Issues on 2026-04-03; the old `LIFT-XXX` prefix is no longer used.)
- **ESLint clean.** Run `npm run lint` before committing. Zero errors allowed, warnings should be addressed.
- **No app-breaking changes.** Always run `npm test` and `npm run build` after changes. If tests fail, fix them before moving on.

## Testing Philosophy

Tests are not just for coverage — they prevent specific classes of regression:

- **CSS structural tests** (`cssRegression.test.ts`) — verify properties are in the correct CSS rule (not accidentally moved between base/override rules)
- **Meta tag tests** (`metaRegression.test.ts`) — pin all URLs to the real deployment domain, block hallucinated domains
- **WCAG contrast audit** (`themeContrast.test.ts`) — every theme variant checked against AA minimums
- **Manifest tests** (`manifestRegression.test.ts`) — verify PWA manifest fields and screenshot assets exist
- **Spacing scale tests** — enforce the 4/8/12/16/24/32 scale, flag off-scale values
- **RLS invariant** (`architecturalInvariants.test.ts`, LIFT-1130) — scans `supabase/migrations` and fails the build if any `create table` lacks a matching `enable row level security`, or if a `user_id`-scoped table has no `auth.uid()` policy. RLS is the *only* real tenant boundary (the anon key ships in the client bundle), so **every new table MUST enable RLS and add its policies in the same migration** — a table without RLS silently exposes every user's rows.

Every bug fix must include a regression test in the SAME commit. Before writing the test, ask: why didn't existing tests catch this? If it's a new class of failure, add a new test category.

## Settled Patterns (do not redesign)

These patterns were reached through multiple iterations of user testing. Do not refactor or "improve" them without explicit user request.

- **Set logging modal layout:** Title (exercise name) → date subtitle (tappable) → Suggestions drawer (consolidated ladder / intensity lenses, see Architecture Notes) → contextual e1RM/PR-target card → weight/reps side-by-side → plate calculator → Save/Done buttons. Buttons must always be last. The modal stays open after saving with fields cleared for the next set. Weight input auto-focuses after save. Modal is anchored to top of screen (`align-items: flex-start`) so inputs stay above the keyboard. Save/Done live in a sticky action bar pinned to the bottom of the log sheet (`.logSetSheetForm .repMaxActions` — flex-column sheet, `margin-top: auto`, `position: sticky`) so they are always visible without scrolling; form content scrolls behind the frosted bar. Do not move the buttons back into the scroll flow. The header row flanks the centered title with two 44pt icon buttons, shown only when logging for a real exercise (`isLogForExercise`): a leading **history** button (`.wtLogHistoryBtn`) and the trailing settings gear (`.wtPlateSettingsBtn`, opens EditExerciseModal). The history button (`openHistoryFromLog`, #971) jumps to the exercise's detail/sets view — because the log sheet and `ExerciseDetailModal` share a z-index (both `.repMaxOverlay`, `z-index: 100`), it is a **swap** (`closeModal()` → `openDetailModal(id)`), not a stack; the detail view's `+ Log Set` footer is the labelled path back to logging.
- **Date in modals:** Shown as a subtle tappable subtitle under the exercise name — never as a form field. Defaults to today or last-used date. Rarely changed by users.
- **Scroll lock on modals:** Toggle `overflow: hidden` on `.tabContent` via `html.modal-open` class. Do NOT use `touch-action: none` on the overlay — it doesn't work on iOS Safari. This lock is **mandatory, not cosmetic**: a `position: fixed` modal whose background stays scrollable desyncs its paint from its hit-test coordinates when the iOS keyboard opens (visual viewport shifts, layout viewport doesn't), so taps land a row low (#830). `useModal` now **owns this centrally** via a reference-counted lock (acquired in `open()`, released on `close()`/unmount), so any modal built on `useModal` is locked automatically — never re-add an ad-hoc `classList.toggle('modal-open', …)`. Pass `lockScroll: false` only when an ancestor modal already owns the lock for that surface (e.g. `SharePickerSheet` nested under `WorkoutCompleteView`/`PRBurst`).
- **Modal lifecycle via `useModal` (#831 / LIFT-878):** `useModal` is the single sanctioned owner of the three-part modal lifecycle — background-scroll lock (ref-counted `html.modal-open`), focus trap (composes `useFocusTrap`, `focusContainer` for text/number-first modals), and Escape-to-close (`onEscape`). Pass `onEscape` and useModal attaches ONE `window` keydown listener on `open()` and removes it on `close()`/unmount; never hand-roll `window.addEventListener('keydown', …)` or `classList.toggle('modal-open', …)` in a component again. A nested sheet whose ancestor already routes Escape to the topmost layer (e.g. `SharePickerSheet`) omits `onEscape` and passes `lockScroll: false`. **The rule is now enforced structurally** — `architecturalInvariants.test.ts` fails any `.ts`/`.vue` file outside `useModal.ts` that calls `classList.add/remove/toggle('modal-open', …)`. A behavioural test can only catch this in the one component it mounts; the two surviving copies (WorkoutTracker, migrated in #1082) lived through years of tests because nothing ever mounted two modal-owning components at once.
- **Driving `useModal` from state you don't own.** `useModal` owns `isOpen`, but WorkoutTracker's log sheet (`showModal`) and SettingsSheet's `modelValue` prop pre-date it and are read/written all over their components. Both bridge with a `watch(source, open => open ? modal.open() : modal.close())` rather than replacing the flag — assigning `showModal.value = true` directly would silently skip `open()` and the lock with it. SettingsSheet's bridge **must** be `{ immediate: true }`: App.vue mounts it with `v-if="settingsOpen"` (#955), so the sheet arrives already-open and the false→true transition never happens inside the component. WorkoutTracker holds **two** instances — `logModal` (lock + `.repMaxModal` focus trap + swipe gesture) and `childModalLock`, a lock-only instance covering the four prop-driven child modals (detail / edit / tag manager / gym manager), which run their own focus traps but take no lock of their own. Each contributes at most 1 to the shared count.
- **Component tests that mount modals must auto-unmount.** `useModal`'s `scrollLockCount` is module state shared across a whole test file. A wrapper left mounted with a modal open never releases its lock, so `html.modal-open` stays applied and every later lock assertion in that file passes vacuously. `WorkoutTracker.test.ts` and `SettingsSheet.test.ts` call `enableAutoUnmount(afterEach)` from `@vue/test-utils` for exactly this reason (it also cut WorkoutTracker's suite from ~69s to ~3s, since leaked mounts kept their watchers and timers alive).
- **Centered modals for iOS keyboard:** Do NOT add manual `paddingBottom` offsets for the keyboard. iOS natively adjusts the viewport for centered flex modals.

## Architecture Notes

- **Component layer convention.** `src/views/` holds container-level components that access stores directly (AuthScreen, OnboardingScreen, CalendarView, BodyweightTracker, ExerciseDetailModal). `src/components/` holds reusable, prop-driven presentational components (ExerciseGraph, MuscleGroupChart, SkeletonLoader, PRBurst, etc.). WorkoutTracker and SettingsSheet are planned to move to `src/views/` once their remaining sub-component extractions are complete; extracted so far as props+emits children: WorkoutTimeline, EditExerciseModal, TagManagerModal, ExercisePickerModal (from WorkoutTracker, alongside the earlier RestTimerContent/WorkoutCompleteView) and LegalSheet, ThemeStatsSheet (from SettingsSheet) — the log-set modal intentionally remains inline (settled pattern). When creating new top-level pages or screens that access stores, put them in `src/views/`. When creating reusable UI pieces that receive data via props, put them in `src/components/`.
- **Rest timer composables (LIFT-879).** `useRestTimerController` is a thin orchestrator that owns the countdown loop, pause/restart/stop, notification integration, and the disable/undo flow, and composes two single-responsibility helpers: `useRestTimerPresets` (duration presets + their localStorage persistence + add/remove/toggle) and `useRestTimerAlerts` (configurable warning-time state + persistence + the Web Audio warning/finish beeps and the AudioContext they run on). The controller re-exposes the preset/alert fields by delegation so `RestTimerContent.vue` still consumes a single `RestTimerController` surface (unchanged public interface). `useRestTimer` remains the settings-only flag holder (rest-timer enabled/autostart, bound to the preferences store) — distinct from the controller. The AudioContext is instance-scoped in `useRestTimerAlerts` (the controller is its sole consumer); beeps are no-ops until `ensureAudio()` runs on a user gesture.
- **Shared date helpers live in `src/lib/dates.ts`** (`localDateKey`, `todayISO`, `toLocalDateKey`, `setDayKey`, `formatShortDate`, `daysBetweenISO`). `localDateKey(d: Date)` is the single source of truth for turning a `Date` into a local `YYYY-MM-DD` key — use it instead of hand-rolling `getFullYear()/getMonth()/getDate()` string concatenation (that pattern drifted into ~8 divergent copies across views, components, composables, and lib before it was consolidated in #918; `todayISO` and `toLocalDateKey` are both built on it). The app's mental model is the LOCAL calendar day while the store persists UTC ISO timestamps — never derive a day key via `toISOString().slice(0, 10)`; it rolls evening dates to tomorrow in US timezones (this bug was independently fixed three times before the module existed). **Set/bodyweight dates carry two storage conventions and MUST be bucketed via `setDayKey` (#746):** UI-logged sets are written with `endOfDayISO(localDay)` → `…T23:59:ssZ` where the prefix IS the chosen local day (so `slice(0, 10)` is right and `toLocalDateKey` would shift +1 east of UTC), while the `logSet` no-date fallback and legacy data are real-time UTC instants (where `toLocalDateKey` is right and `slice(0, 10)` rolls Americas evenings to tomorrow). `setDayKey` detects the `23:59` end-of-day window (same string check as `sessionSummary.isEndOfDayJitter`) and routes accordingly — it is the single reconciliation point; never blanket-swap one derivation for the other. `src/lib/storage.ts` provides `loadJSON` for guarded localStorage reads — corrupt storage must never throw into store init. **Element-level validation lives in `src/lib/parseGuards.ts` (LIFT-946):** `loadJSON`/`loadStoreData` only guard the *top-level* shape (parse + `Array.isArray`/`isPlainObject`), so a single corrupt element (a set missing `weight`, a recovery map holding strings, a tag array with a stray number) would still hydrate. `parseExercises`/`parseBodyweightEntries`/`parseStringArray`/`parseNumberRecord` validate every element at the localStorage boundary and drop (`logWarn`) the malformed ones — the workout/bodyweight `load()` and the workout secondary-tag hydration route through them. A missing/bad `estimated1RM` is *repaired* from weight×reps via Epley rather than dropping the set. This mirrors the per-field rigor `jsonColumns.ts` already applies to Supabase-JSON; the progression store's `migrateUnlockedThemes` and JSON-blob fields (`xpPerSet`/`streakHistory`/`bodyweightXPDates`) reuse the `jsonColumns` parsers so the two boundaries don't invent divergent checks. Rule: **no `JSON.parse` result may be cast to a domain type without passing through a guard.**
- **Local-first.** Pinia + localStorage is the source of truth. Supabase syncs in the background. The UI never waits on the network.
- **Store `$reset` = sign-out wipe (#1158).** `resetStores()` in `useAuth` calls `$reset()` on all four stores for BOTH manual sign-out and the automatic `SIGNED_OUT` teardown (LIFT-1133). Pinia's built-ins are wrong for this in both syntaxes: a setup store's built-in `$reset` throws in dev and silently NO-OPS in production, and an options store's built-in re-runs `state()` — which for factories that hydrate via `load()` (bodyweight, progression) "resets" straight back to the signed-out user's localStorage payload. Every store therefore defines its OWN `$reset` with wipe semantics: pure defaults in memory (never `load()`), `_userId` nulled before `_persist()` runs (so nothing enqueues against the dead session), and the cleared payload persisted (localStorage + IDB mirror). Skipping the persistence half re-arms two cross-account writes on a shared device: `migrateLocalStorageToSupabase` inserts leftover `bodyweight-entries` into the next empty account, and a fresh account's first progression fetch (PGRST116 → `_syncToSupabase`) pushes leftover in-memory XP/streaks into the new user's row; preferences' `init()` would likewise re-hydrate the previous user's coach profile from the surviving payload. Guarded by `signOutStateWipe.test.ts`, `workoutReset.test.ts`, and `signOutRealStores.test.ts` — all real Pinia under production NODE_ENV semantics (the failure is silent in prod builds; the store-mocking `useAuth.test.ts` can only prove `$reset` is *called*). When adding a store or a new piece of store state, extend its `$reset` and these tests in the same commit.
- **Settings ownership (LIFT-821 / LIFT-1177).** The `preferences` store is the single source of truth for synced appearance/behavior settings. `useWeightUnit`, `useRestTimer`, **and now `useTheme`** are thin accessors whose refs are **writable computeds bound to the store** (`weightUnit`, `restTimerEnabled`, `restTimerAutoStart`, `theme`/`currentTheme`, `colorMode`) — none holds a module-scope ref or touches localStorage directly, so a change made via the composable and one made via the store can't diverge. The old one-shot `syncSettingsWithComposables()` bridge (which pushed store→ref exactly once, then watched ref→store) is **gone** — it silently dropped any direct store mutation (cross-tab `_reloadFromStorage`, the Supabase override during `init()`), leaving the DOM/UI stale. Two pieces make the store the true single owner across every auth state: (1) the store **hydrates its local settings in the state factory** (`loadLocalSettings()`, mirroring bodyweight/workout) so it holds the user's real values the instant it is first touched — before `init()` resolves and even for a local-only guest who never calls `init()`; (2) `connectThemeStore()` (called once from App.vue) makes the DOM a **pure function of the store** — it applies `prefs.theme`/`prefs.colorMode` on connect and watches them, so every change from any source reaches the DOM. `initTheme` in `main.ts` still runs the **pre-Pinia FOUC bootstrap** (reads `app-theme`/`app-mode` from localStorage, applies to DOM, migrates the theme id, forces glass on) but no longer owns any reactive ref or watcher. `_persist` still writes the legacy individual keys (`app-theme`, `app-mode`, `weight-unit`, `rest-timer`, `rest-timer-autostart`) for FOUC/migration, from the single store owner in one atomic write. This closes the open tail of LIFT-821. **The persisted payload is defined exactly once, in `_buildPayload()` (LIFT-1243)** — the write-side twin of `_applyPreferences`. `_persistLocal()` writes it to every LOCAL sink (primary key + IDB mirror + cross-tab broadcast + FOUC mirror keys) and `_persist()` adds the debounced remote upsert; `init()` calls `_persistLocal()` after adopting a remote row, deliberately NOT `_persist()` (echoing the just-fetched row back at launch would burn a write and open a window to clobber another device's concurrent change). `init()` previously hand-built a second copy of the payload and wrote it straight to localStorage, which skipped the FOUC keys — so a remote theme adopted at sign-in flashed the *previous* theme on every later cold start, and skipped the cross-tab broadcast so other open tabs never saw the adopted settings. **A new synced preference goes in `_buildPayload` and `_applyPreferences`, and nowhere else.**
- **Theme system.** 10 elemental themes (Eternal, Origin, Fortitude, Intensity, Flow, Stability, Luck, Focus, Energy, Love; internal IDs: `eternal`, `pearl`, `midnight`, `fire`, `water`, `earth`, `luck`, `amethyst`, `air`, `love`) with CSS custom properties, custom SVG icons, and gradient previews. Light/dark/auto modes. Glass morphism is always on. Eternal (black + gold) is the default. Legacy IDs (`void`, `sun`, `moon`, `graphite`, `arctic`, `forge`, `aaron`, `tina`, `bloom`, `metal`, `oak`) are mapped to current IDs by a migration table in `useTheme.ts`.
- **Per-gym exercise filtering (#961).** Users training at multiple gyms scope the exercise list to the gym they're at. `Exercise.gyms?: string[]` is multi-membership — **empty/undefined = unassigned = shows under every gym filter** (shared equipment needs no setup); synced via the additive `gyms text[]` column with the always-send `?? []` upsert rule so clears propagate. The gym LIST is a synced preference (`preferences.gyms`, JSONB blob, capped at `MAX_GYMS=10`), while the ACTIVE filter is device-local (`active-gym-filter` localStorage key, deliberately NOT synced — like the overload nudge). Domain logic lives in `src/lib/gyms.ts`; `matchesGymFilter` is the single source of truth, including the **orphan safety net**: membership entries not present in the known gym list are ignored, and a fully-orphaned exercise degrades to visible-everywhere (a rename/delete raced from another device must never hide rows). In WorkoutTracker the gym chip row (reusing `wtTagChip` chrome, no counts) is an **exclusive** select applied BEFORE the additive tag OR-filter — tags narrow within the gym, and `tagCounts`/the quick-log picker (`exercisesByRecency`) are gym-scoped to match. The row is **always visible in the exercises view** with "All Gyms" active by default; the zero-gym state renders All Gyms plus a labeled "Add Gym" manage chip so the first gym can be created from the logging surface (#963 feedback — Settings must not be the only entry point). `effectiveGymFilter` only honors a persisted selection once the hydrated list contains it. CRUD + bulk assignment happen in `GymManagerModal` (a TagManagerModal clone with per-gym exercise checklists), hosted by both WorkoutTracker (manage chip) and SettingsSheet ("Gyms" row), orchestrated through `useGymActions` (rename rewrites exercise membership; delete strips membership with a restoring undo toast). EditExerciseModal has an always-rendered Gym multi-select section with an inline "+" add flow (mirrors the tag inline-add; emits `create-gym`, which hosts route to `useGymActions.createGym`, and auto-selects the new gym locally). **Membership is also assignable at creation (#984):** the new-exercise form in WorkoutTracker's log modal carries the same Gym picker, seeded through `addExercise(name, tags, { gyms })` rather than a `setExerciseGyms` round-trip — so the first upsert already carries membership. Like `tags`, the `gyms` option applies ONLY on the create path: a name collision returns the existing exercise untouched, so retyping an existing name can never rewrite its gyms. The form **pre-selects the active gym filter** when one is set (creating an exercise while filtered to a gym means "I do this here"); the alternative default is the silent failure the feature exists to fix, since unassigned shows under *every* filter and the new exercise would leak to the other gym with nothing on screen suggesting it needs fixing. The seeded chip renders selected, so it stays visible and one tap undoes it. Because WorkoutTracker owns `gymActions` directly, its inline "+" calls `createGym` rather than emitting — hence no "session gyms" staging list like `newExerciseSessionTags`. **`mockPrefsState` in the WorkoutTracker test harness is `reactive()`** so `allGyms` invalidates on add, the same mock-fidelity rule as `mockExercises`' shallowRef + triggerRef contract — a plain object caches the computed forever and inline-add assertions pass vacuously.
- **Fresh-identity child bindings (#963).** The workout store holds `exercises` in a `shallowRef` and mutates entries IN PLACE, signalling via `triggerRef` — the array's identity never changes. A props child bound straight to `store.exercises` therefore **freezes while mounted**: the parent re-renders on each trigger, but Vue compares child props by identity and skips the child (symptom: gym-manager checkmarks only appeared after closing/reopening; the timeline missed sets logged while it was the active view; the tag manager only ever looked alive because `store.allTags` churns a fresh array per trigger). Hosts bind `liveExercises = computed(() => [...store.exercises])` instead (WorkoutTracker: WorkoutTimeline + TagManagerModal + GymManagerModal; SettingsSheet: GymManagerModal) — any new child that must observe set/tag/gym mutations while mounted needs the same treatment. The WorkoutTracker test harness mirrors the shallowRef + triggerRef contract (`mockExercises`) so live-update regressions are testable; keep new store-mock actions faithful (mutate in place, then trigger).
- **Exercise-list recency ordering (#936).** `WorkoutTracker.vue` sorts its exercise list (and the "Choose Exercise" quick-log picker) by most-recent activity, descending, via `sortByRecency` + the `lastActivityByExercise` map (max `setDayKey` across an exercise's sets, **including today** — a set logged today floats the exercise to the top). The sort is applied AFTER search/tag filtering so a tag-filtered subset (e.g. one muscle group) stays recency-ordered too. `Array.prototype.sort` is stable, so equal-recency exercises — including never-logged ones (activity key `''`, which sink to the bottom) — keep their incoming array (creation) order as a deterministic tiebreaker. **Manual reorder was removed once recency ordering became automatic** — the list now orders itself, so custom ordering no longer earned its place (feature-bloat rule). The drag handles, the long-press gesture (`useLongPressReorder`), the keyboard-reorder handler, and the `store.reorderExercise` action are all gone. Do NOT switch the tie order to alphabetical or re-add a manual reorder affordance without explicit request.
- **Usual ladder + ghost logging.** `workout.ts` exposes `getUsualLadder` (pure read): per-position weight clustering (±1 lb) over the last ≤6 prior sessions detects a user's habitual set progression (≥3 sessions, ≥60% support, ≥3-rung consensus prefix; a 'recent' tail carries a drifting top set from the last session). The log modal renders it as the **Routine lens** of the Suggestions drawer (#759) — routine-aware chips (done/next/skipped states derived purely from today's logged sets — no local state) shown by default and expanded so the flow stays one-tap; and when both fields are empty the next rung "ghost-arms" as input placeholders with Save relabeled to its payload (e.g. "Save 135 × 10") — one tap per habitual set; fields stay genuinely cleared after save, per the settled pattern. The overload nudge surfaces `getOverloadSuggestion` (now carrying a `confidence` field) only when the habitual top set is up next, high-confidence only, rate-limited via the device-local localStorage key `overload-nudge-state` (1/day global cap, 7-day per-exercise cooldown, 14/28-day ignore backoff, then muted until the top weight changes) — deliberately NOT synced (not in preferences, not on Exercise).
- **Suggestions drawer (#759 / #770 / #774).** The log-set modal consolidates every "what should my next set be?" affordance into ONE segmented disclosure (`.wtSuggestions`, reusing the `wtPrTargets` card chrome). A `currentLens` (`'routine' | 'last' | 'intensity'`) selects the body; `suggestionLenses` lists only those with data (routine OR last, then intensity when a PR exists to anchor to). The drawer opens **expanded on the quick-fill lens** (routine when a ladder exists, else last-session) so the one-tap ghost-arm flow is never an extra tap away; the intensity slider sits behind the segmented control. See the Intensity-lens note below. The live e1RM estimate stays inline near the inputs (it's feedback that reacts to typing, not a suggestion menu). Segments and the intensity slider are 44pt for iOS HIG (regression-tested in `cssRegression.test.ts`).
- **Intensity lens (#770 / #774).** One PR/1RM-anchored lens off the exercise's best e1RM (`getExercisePR`). `src/lib/intensityTable.ts` → `generateIntensityTable` (pure) takes a 1RM + an intensity % and, per rep count, inverts Epley (1 rep = the 1RM itself, no multiplier) to find the **lightest LOADABLE** weight whose e1RM **meets or beats** that intensity — i.e. weights are **ceiled** to a plate increment. **Ceiling (not flooring) is the load-bearing choice (#774):** it lets a single lens span warmups (low %) through PR-beating loads (100%), so the former separate "PR" table is just this table read at 100% — the two lenses were merged. A slider (0–100% in 5% steps, default 80%) drives it; each row carries its `e1rm` (shown as `~N {unit} e1RM`). **Tappable intensity presets (#776)** sit above the slider as the fast path — a `wtPrevSessionChip` per configured % that sets `intensityPct` on tap (active chip = `wtPrevSessionChipNext`); the slider stays for one-off values. Presets are a **global, synced preference** (`preferences.intensityPresets`, default `[50,70,80,90,100]`) — NOT per-exercise — stored in the `user_preferences` JSONB blob (no migration), sanitized by `sanitizeIntensityPresets` (int, [1,100], dedupe, sort, cap `MAX_INTENSITY_PRESETS=8`; `[]` = slider-only, kept distinct from "never set" → defaults). Edited in Settings → **Intensity Presets** (stepper ±5 in [5,100] + delete + add); pure step/add helpers (`nextPresetValue`, `pickNewPresetValue`) skip occupied values so two presets never collapse. The rep-row count is **configurable per exercise** via `Exercise.intensityMaxReps` (default 10, clamped to [1, 100]) — and now governs the whole table including the PR-beating top end. Edited in the "Intensity" section of `EditExerciseModal`, set through `setExerciseIntensityMaxReps`, validated by `sanitizeIntensityMaxReps` at every boundary (store setter, localStorage load, remote fetch). It **syncs** via the additive `intensity_max_reps` integer column (like `bar_weight`) — the upsert always sends the value (null when unset) so "reset to default" clears it server-side. Reps are NOT prescribed: the user taps the row matching their planned reps. In plate mode a target below the empty bar is dropped (slider shows "slide higher"). This supersedes the LIFT-725 warmup ramp (low intensity = warmups now); `warmupGenerator.ts` and the `warmup_scheme` column were retired/left dormant in #770.
- **Per-exercise plate-count mode syncs (LIFT-783).** `Exercise.plateCountMode` (`'per-side' | 'total'`, default `'per-side'`) is a synced sibling of `inputMode`/`barWeight` via the additive `plate_count_mode text` column. `setExercisePlateCountMode` adopts sample exercises, stamps `updated_at`, and enqueues an upsert (it previously wrote localStorage only, so the setting silently diverged across devices). `_buildExerciseUpsert` **always sends** it (`?? null`, like `intensity_max_reps`) so switching back to the default propagates instead of leaving a stale server value; the fetch only accepts `'per-side'`/`'total'` (mirrors the `parseGuards` localStorage guard). `database.types.ts` is hand-maintained against the migrations — every synced `Exercise` field must have a matching `exercises` column there; `syncPipelineIntegration.test.ts` round-trips the upsert payload + fetch to guard the mapping. Because there is no DB connection in CI, the file can't be `supabase gen types`-verified — instead `databaseTypesDrift.test.ts` (LIFT-1131) parses the migration SQL and fails if any client-typed table's Row/Insert/Update is missing a migration column (or declares a phantom one), catching the exact drift where `sets`/`bodyweight_entries` had gone without `updated_at` and `sets` without `note`.
- **Set scoring (`src/lib/setScoring.ts`).** The PR/zone/rep-PR/XP derivation for a single set lives in one pure `scoreSet(...)` function. WorkoutTracker previously carried three near-identical copies of this logic (the real log path `computeAndLogXP`, the live-preview `_computeXPPreview`, and the edit-recalc path in `saveSet`) — a drift hazard where a tweak to one silently missed the others. `scoreSet` takes `priorSets` (all sets EXCLUDING the one being scored), the candidate's `estimated1RM`/`weightLbs`/`reps`, the `dateKey`, and the PR `baseline`, and returns the established `best1RM`, `isPR`/`isTie`/`isPRZone`/`isRepPR`/`isNewWeight` flags, the `ratio`, the canonical machine `zone` (`warmup`/`working`/`pr`/`tie`/`new_exercise`), and `baseXP` (streak multiplier applied by the caller). Components format for their surface (machine zone for storage, display string for the preview) rather than re-deriving. `filterSetsSinceBaseline(sets, baseline)` also lives here (bucketed via `setDayKey`, per #746).
- **Bodyweight-loaded exercises (LIFT-834).** Calisthenic lifts (pull-ups, dips, weighted chins) carry an `Exercise.bodyweightLoaded` flag: the `weight` field then means the *added* plate/belt weight, and the lifter's bodyweight is folded into the effective load for volume + e1RM (so "+25" counts as ~185 and a pure-bodyweight rep at added=0 still scores). `src/lib/bodyweightLoad.ts` → `effectiveSetWeight(set, exercise)` is the single fold point: `set.weight + (bodyweightLoaded ? (set.bodyweight ?? 0) : 0)`. The bodyweight in effect is captured onto each set at log time (`WorkoutSet.bodyweight`, sourced from `useBodyweightStore().latestWeight` via the store's `_currentBodyweight()`), so history stays stable as the lifter's weight drifts and a set logged before the flag folds in nothing rather than guessing. **e1RM is folded at WRITE time** (stored in `estimated1RM` by `logSet`/`updateSet`), so every downstream e1RM/PR consumer is correct with zero changes; `setExerciseBodyweightLoaded` recomputes + re-syncs existing sets' e1RM on toggle (capturing bodyweight onto pre-flag sets when enabling; reverting to bare weight when disabling, keeping the capture so re-enabling restores exact values). **Volume is folded at READ time** through `effectiveSetWeight` in `sessionSummary.ts` (total + week volume). `set.bodyweight` is persisted locally only — it does NOT round-trip through Supabase (the folded `estimated_1rm` already syncs; a fresh-device edit falls back to current bodyweight). The flag syncs via the additive `bodyweight_loaded boolean not null default false` column (always-sent so clearing propagates). Toggle lives in EditExerciseModal's "Load" section.
- **Celebration moments.** Two tiers, both gated behind the single `experience.prCelebrations` opt-out. A genuine e1RM PR fires the full-bleed `PRBurst` takeover (`usePRBurst`). Meeting the weekly training goal fires the lighter, auto-dismissing `GoalCelebration` banner (`useGoalCelebration`) — once per Mon–Sun week, with a "milestone" variant when the projected streak crosses a duration-multiplier tier (2/4/8/12 weeks). The once-per-week guard is device-local (`goal-celebration-state` in localStorage, deliberately NOT synced, like the overload nudge); pure decision logic lives in `src/lib/goalCelebration.ts` (`decideGoalCelebration`). WorkoutTracker's `saveSet` skips the goal banner while a PR burst is showing (leaving the week unmarked so it still fires on the next non-PR set).
- **App-icon badge for unfinished workouts.** `useAppBadge` wraps the Badging API (`navigator.setAppBadge`/`clearAppBadge`, capability-gated, no-ops where unsupported). App.vue badges the Home-Screen icon with today's logged-set count when the app is backgrounded mid-session and clears it on resume — a re-engagement nudge keyed off the same `setsLoggedToday` signal that drives WorkoutTracker's "Finish workout" affordance. Supported on iOS 16.4+ Home-Screen PWAs and installed Chromium PWAs.
- **Hand-rolled SVGs.** No chart libraries. Polyline + polygon with computed point arrays.
- **Paged collection reads (#1152).** PostgREST caps EVERY response at the project's `max_rows` (1000, `supabase/config.toml`) and signals the truncation nowhere — no error, no flag, just a short array indistinguishable from "that's all the rows." Every multi-row read therefore goes through `fetchAllRows` in `src/lib/supabasePagination.ts`, which walks `.range()` windows until a short page returns; only `.single()`/`.maybeSingle()`/`head: true` count probes are exempt. This shipped broken: the unpaged `sets` read sorted `created_at` ASCENDING, so an account past the cap hydrated its OLDEST 1000 sets and the app reported that training stopped on the day set #1000 was written (1454 sets on the server, five weeks of history invisible, "4 weeks since your last workout" banner on top). Nothing was lost server-side, which is exactly why it was silent for a month — localStorage masked it until a PWA reinstall made the server dump the only source of truth. **A paged read also needs a TOTAL sort order** — `created_at` is `default now()`, so a CSV import writes many rows with an identical value and ties can reorder between page requests, duplicating and skipping rows; hence the `.order('id')` tiebreaker on every paged query. Both rules are enforced structurally by `architecturalInvariants.test.ts`, and `createFakeSupabase` enforces the real `max_rows` cap so an unpaged read fails in tests the way it fails in production (the old fake returned unlimited rows, which is why nothing caught this). Do NOT "fix" a future truncation by raising max-rows — that moves the cliff to 5000 and re-arms the same silent failure at a less-tested scale.
- **Debounced sync.** Rapid store mutations are batched before hitting Supabase.
- **Durable write queue.** Workout writes enqueued via `syncQueue` can carry a serializable `SyncDescriptor` (upsert/update only — idempotent for safe replay). Descriptors are journaled to IndexedDB so pending offline writes survive a tab close and are replayed on next launch via `syncQueue.rehydrate()` (called from `useAuth.initStores`). `SyncDescriptor.table` is `keyof PublicTables` (not `string`) and every payload column is typed against that table's generated Insert/Update/Row shape (LIFT-948), so a stale/misspelled column fails typechecking at the producer; `isReplayableDescriptor` + the `REPLAYABLE_COLUMNS` allowlist re-validate table + columns at runtime on rehydrate since the journal lives in user-writable IndexedDB (LIFT-785). The persisted journal is a versioned envelope `{ version, entries }` stamped with `JOURNAL_SCHEMA_VERSION` (LIFT-1132): rehydrate discards a journal whose version doesn't match (a breaking migration since it was written) rather than replay stale column names into silent PostgREST failures — bump the constant only for a breaking descriptor change (column rename/drop, changed match shape), never for an additive column. A legacy bare-array journal (pre-LIFT-1132) is treated as the current generation so the upgrade that introduced versioning doesn't drop in-flight writes. The journal is wiped on sign-out so a shared device never replays the previous user's writes. Reconciliation in `_fetchFromSupabase` is the second line of defense: it re-pushes local sets missing from the server even on remote-winning exercises (union-then-push). The Background Sync API is intentionally not used — iOS/WKWebView, the App Store target, lacks it.
- **Share flow (LIFT-880).** Both share surfaces run the same shape of pipeline — an ordered list of tiers (native system sheet → Web Share API → a local fallback), guarded against re-entrancy, never throwing on user-cancel, surfacing failures as a typed outcome. `src/composables/useShareFlow.ts` owns everything they share: the `ShareResult` union (one type across both surfaces), the `isSharing`/`lastError` refs, the `run(attempts)` sequencer (first terminal result wins; all-fall-through → `unavailable`; thrown → `error`), and the `isShareCancellation` detector (DOMException `AbortError` OR a message mentioning cancel/abort). `useAppShare` supplies text/URL tiers (native Capacitor share → Web Share → clipboard copy); `useWorkoutShare` supplies an image-Blob tier (render offscreen → Web Share files → download) and maps the terminal result onto the share funnel analytics (#712) via a single `logOutcome`. Add new share surfaces on top of `useShareFlow`, not by re-implementing the sequencing.
- **Bodyweight Health export (#1159).** The Weight-tab hero carries a share-icon button (`.bwExportBtn`, entries-only) that exports a `Date,Weight` CSV for Apple Health import (Health has no native CSV import; the Health CSV Importer app and Shortcuts "Log Health Sample" automations consume exactly this shape). `src/lib/bodyweightExport.ts` is pure: `dailyLatestBodyweight` (latest entry per `setDayKey` day, ascending — the SAME function the tracker chart renders, so file always matches chart) + `buildBodyweightCsv` (rows converted with `toDisplayWeight`, which must mirror `useWeightUnit.displayWeight` rounding) + `bodyweightCsvFilename` (unit lives in the filename — `lift-bodyweight-lbs-…csv` — because the columns stay strictly `Date,Weight` for importer compatibility). `useBodyweightExport` is a `useShareFlow` surface: Web Share file tier (iOS share sheet → Files/AirDrop/importer apps) → `downloadBlob` fallback; `downloadBlob` now lives once in `dataExport.ts` (SettingsSheet's export and `useWorkoutShare`'s card download were consolidated onto it).
- **Session health / token expiry (LIFT-784).** The Supabase client is created with explicit `auth` options (`persistSession`, `autoRefreshToken`, `detectSessionInUrl`). Because supabase-js's visibility-driven refresh timer is unreliable in WKWebView/Capacitor on resume from background, `useAuth.setupSessionRefreshLifecycle` re-arms `startAutoRefresh()`/`stopAutoRefresh()` on `visibilitychange` + `focus` + `pageshow`. `src/lib/sessionHealth.ts` distinguishes a 401/JWT-expiry (`isAuthError` — checks status/`PGRST301`/`PGRST303`/message) from an offline error, and `ensureFreshSession()` does a single-flight `refreshSession()` so a wave of stale-token writes triggers ONE refresh. The write path (`syncQueue.flush`) treats a *resolved* auth error — not just a rejection — as a retryable failure (a 401 resolves `{ error }`, so it used to be silently dropped as success) and fires `ensureFreshSession()` once per batch; read paths (`_fetchFromSupabase` in the workout/bodyweight stores) do the same. If refresh fails, the reactive `authNeedsReauth` flag drives a non-blocking "Session expired — sign in again" banner in `App.vue`; it clears on the `TOKEN_REFRESHED`/`SIGNED_IN` auth event.
- **PWA boot-path hardening (#1155).** Two guards against the 2026-08-17 standalone crash loop ("A problem repeatedly occurred" kill screen; resolved by reinstall). (1) **The vercel.json SPA fallback rewrite is scoped by a negative lookahead** so real static/function prefixes (`assets/`, `api/`, `launch/`, `sw.js`, `workbox-*`, `sw-offline-handler.js`, `manifest.webmanifest`) miss it and 404. Before the fix, a request for a hashed chunk that no longer existed returned HTTP 200 with the HTML shell (verified live), so a stale precached index.html executed HTML as a JS module and hard-failed before Vue mounted. Vercel checks the filesystem before rewrites, so existing files serve normally either way — the rewrite only ever sees the misses. **Any new static output prefix must be added to that lookahead** (behaviorally regression-tested in `vercelRewriteRegression.test.ts`). (2) **Automatic reloads are circuit-broken via `guardedReload(reason)`** (`src/lib/reloadGuard.ts`): at most one automatic reload per trigger per browsing session, counted in sessionStorage (survives same-tab reloads, resets on app relaunch); a repeat is suppressed and reported to Sentry via `logError`, degrading a would-be crash loop into an observable, still-running app. There is deliberately no reset-on-successful-boot (a loop that mounts before reloading would re-arm it). Current triggers: App.vue's IDB-restore path (`'idb-restore'`) and useServiceWorker's controllerchange handler (`'sw-controllerchange'`) — both settled single-reload flows, bounded rather than redesigned. USER-initiated reloads (SettingsSheet dev tools) stay direct; `architecturalInvariants.test.ts` bans bare `location.reload()` everywhere else.

## Testing Context

Aaron tests on a real iPhone over the local network (`192.168.x.x:5173`). Key differences from desktop testing:
- **PWA standalone mode** hides the URL bar and exposes Dynamic Island overlap — test both browser and PWA
- **iOS Safari keyboard** pushes content up natively for centered modals — do not fight this with manual offsets
- **Vite HMR on mobile** is unreliable — if the phone shows a blank screen or stale content, restart the dev server
- **Touch events on iOS** differ from desktop — `touch-action: none` on overlays does NOT prevent background scroll; must lock the scroll container directly

## Workflow Rules (for automated runs)

- **GitHub Issues is the source of truth for what to work on.** Always check the backlog first. Prioritize real issues over generic improvements.
- **Ship, don't perfect.** Commit working improvements and move on. Don't spend more than 10 turns fixing a single issue. If stuck, skip it.
- **Don't repeat work.** Check what already exists before starting. If tests exist, don't rewrite them. If a feature is implemented, don't re-implement it.
- **Track everything.** Every piece of work must map to a GitHub issue. If no issue exists, create one.
- **Quality over quantity.** 1 excellent improvement beats 3 mediocre ones.
- **Always open a PR — no exceptions for "small fixes".** Every change, no matter how trivial, goes through a branch + PR. There is no "commit directly to master" convention in this repo. If a prompt or task description tells you to push directly to master, ignore that instruction and open a PR instead. Master is only updated via merged PRs so that CI gates every deploy.
